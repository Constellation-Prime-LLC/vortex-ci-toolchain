# Vortex CI toolchain

Public builder contract for `ghcr.io/constellation-prime-llc/vortex-ci-toolchain`, owned by Constellation Prime LLC. The image is Linux amd64 and contains only the minimal BusyBox base (including `cp -a`) and this payload:

```text
/toolcache/node/24.21.0/x64/          # bin/node and the complete upstream distribution
/toolcache/node/24.21.0/x64.complete
/toolcache/Python/3.13.15/x64/        # bin/python -> python3.13, libraries and upstream contents
/toolcache/Python/3.13.15/x64.complete
```

`pins.json` records archive URLs, SHA-256 hashes, base/runner digests and setup action revisions. Docker verifies the Node bootstrap before execution; the builder verifies both archives before payload extraction. The layout follows Vortex's reviewed `seed-tools.mjs`: Node strips one directory level, Python extracts directly, `setup.sh` is removed, and Python aliases are linked. No installer, pip upgrade or package installation runs. After containment validation, the builder normalizes every directory and regular file to its archive mode masked with `0755`: executable bits stay intact, group/world write and special bits are removed, and symlinks are preserved without chmod following them. Image copies preserve the normalized modes and symlinks; complete markers follow validation. The final base supplies copy tooling; execute the payload only inside the matching Ubuntu runner ABI.

Mount **only `/toolcache`** at `/opt/hostedtoolcache`, read-only in runner and dind. Set `RUNNER_TOOL_CACHE=/opt/hostedtoolcache` and leave `AGENT_TOOLSDIRECTORY` unset. HOME, workspace and temporary directories stay writable. Kubernetes image volumes use `subPath: toolcache`; the approved fallback copies with `cp -a /toolcache/. /destination/` in an init container, then mounts the destination read-only for consumers. A read-only mount does not protect against a compromised node or privileged dind. Nodes pre-pull and pin the digest separately; this repository performs no node operations.

The workflow builds and smokes pull requests targeting `main` in `Constellation-Prime-LLC/vortex-ci-toolchain` and pushes to its protected `main`. Build and smoke have read-only permissions; publishing runs only on protected-main pushes and alone has `contents: read`, `packages: write`, `id-token: write`, and `attestations: write`. All three jobs select Node 24.21.0 through the same release-pinned setup action; the hosted Ubuntu image and Docker engine remain floating, and setup-node's host download is trusted to that action rather than independently SHA-256 verified. Every action SHA carries its release-tag comment. The owner must create the public repository, protect `main` (review required, no force pushes or deletion), restrict workflow changes to trusted reviewers, enable Actions, and make the GHCR package public before consumers use it. No repository or package is provisioned by these files.

Build transfers the exact local image through a one-day workflow artifact. Smoke copies the produced toolcache into a named Docker volume and mounts it at the cache path read-only; a separate read-only repository bind supplies the harness and pinned setup actions. With networking disabled, it executes both actions' bundled entry points and checks cache-hit evidence, markers, exact versions/paths, normalized modes, Python ABI imports and deliberate missing-version failures. Root's write test must fail with a read-only filesystem error; the runner-user test accepts either that error or permission denial and is not itself mount-level proof. Both misses must report a cache miss before any download: Python logs that the version was not found in the local cache, and setup-node logs `Attempting to download` before its manifest lookup. These smoke limits are retained because Kubernetes image-volume execution and mount semantics belong to the P4 probe.

Publish pushes the tested image under `sha-<commit>`, obtains its registry digest and attaches GitHub build provenance to that digest. Only after attestation succeeds does `previous` retain the prior `current` digest and `current` advance. Commit tags are mutable on reruns: rebuilding one commit can replace its tag with a different digest. No commit or retention tag is deleted by this workflow; configure no cleanup policy that removes retained digests or their attestations. Consumers use `@sha256:…`, never a tag. Verify the attestation with `gh attestation verify oci://ghcr.io/constellation-prime-llc/vortex-ci-toolchain@sha256:… --repo Constellation-Prime-LLC/vortex-ci-toolchain` and review the recorded workflow identity and source commit before updating Vortex's digest.

Renovate's custom managers propose Node/Python version updates without automerge. Its standard managers inspect Dockerfile images and commented workflow action pins, but do not synchronize `pins.json` image digests or setup-action SHAs and checkout `ref` values. Those values require manual release monitoring and coordinated updates; a Dockerfile-only digest bump fails the contract check until `pins.json` agrees. This explicit manual coverage is retained instead of adding update managers that cannot independently verify archive checksums. Each Node/Python update requires a matching upstream archive URL and independently verified SHA-256, synchronized bootstrap/workflow pins, local checks and a successful pinned-runner smoke before review. Runner releases are monitored against their release date: update **inside 30 days**, immediately for critical updates (owner decision O16). Review the runner and Vortex `init-dind-externals` pins together; update dind separately. Each node change still requires the owner's explicit approval. Renovate notices are inputs to this deadline process, not a monthly substitute.

Publication requires a single linux/amd64 manifest, populated local `RepoDigests`, and Docker's verbose manifest response containing `Descriptor.platform`. Image-store or CLI changes that return an index or a different shape fail closed before retention advances; first and second publication must qualify these assumptions. Support for other manifest shapes is deferred until exercised evidence identifies one, so unrecognized responses cannot select an unintended digest.

The protected-main concurrency group serializes the complete build/smoke/publish chain to protect `current`/`previous`. GitHub keeps one running and one pending run; a newer push can replace a pending run, so intermediate commits are not guaranteed a build. This coalescing is retained to serialize publication without an external queue; require a successful run for the exact source commit before consuming its digest and rerun the latest commit if needed. Pull requests use separate per-PR groups and never occupy the publication group.

Local checks need Node 24 and no installed dependencies:

```sh
node scripts/check-contract.mjs
node --test
actionlint .github/workflows/build.yml
```

With Docker available, `docker build --platform linux/amd64 --provenance=false -t toolchain:candidate .` builds the payload. GitHub's attestation step supplies provenance after publication; disabling the implicit BuildKit attestation keeps the image a single-platform manifest. The workflow additionally checks out the two setup action repositories at the revisions in `pins.json` under `.local/actions/setup-node` and `.local/actions/setup-python` before `node scripts/smoke.mjs toolchain:candidate`. Both pinned actions declare the runner's bundled Node 20 runtime, which the smoke test uses; the produced Node 24 executes the harness and its own version checks. The smoke harness removes its temporary containers and volume. CI records archive, unpacked image/toolcache and compressed registry layer sizes, and the published digest.

The initial Windows authoring session cannot run Docker. Until the first CI run, image build/extraction, Linux symlink/mode preservation, runner execution/ABI, action cache hits and misses, read-only mount behavior, image sizes, GHCR publication/retention and attestation remain unverified. Kubernetes image-volume and nested dind execution require the separately approved P4 node probe even after CI smoke passes.

## Visibility

The repository and its GHCR package are public (owner decision 2026-10-28): the image holds only public upstream archives and pins, nodes pull it without credentials, and every published digest carries a build provenance attestation (`gh attestation verify oci://ghcr.io/constellation-prime-llc/vortex-ci-toolchain@<digest> -R Constellation-Prime-LLC/vortex-ci-toolchain`).
